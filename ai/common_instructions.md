# Global AI Instructions

このファイルは全てのプロジェクトで共通して参照されるAIアシスタント向けのガイドラインです。

## 動作原則

- セキュリティに関わる情報（APIキー、パスワード等）は決して出力しない。
- 日本語で回答する（特別な指示がない限り）。
- 実行すべきコマンドや修正箇所のコンテキストを明示する。

## 破壊的な操作は確認を求める

次は実行前に明示的な確認を求める。**機構的に止める仕組みがある環境では、そちらが先に働く**（Claude Code は `~/.claude/settings.json` の `permissions.ask`）。機構が無い環境ではこの節が唯一の歯止めになるので、二重になっても残す。

- `git push`（リモートへの反映）と履歴の改変（`rebase` / push 済みコミットの `amend`）
- 作業ツリーを破壊しうる操作（`reset` / `checkout -- <path>` / `restore` / `clean` / `stash drop` / `branch -D` など、変更を失う恐れのあるもの）
- 広範囲の削除・一括上書き（`rm -rf` / `sed -i` などオプションの綴りを問わず）
- システムや環境全体への変更（`sudo`、OS 設定ファイル群の変更、`apt` / `npm` / `pnpm` / `pip` / `brew` などのグローバルインストール）

## コメント

コメント（JSDoc・`//`・テストの説明文字列・zod/OpenAPI の `description` を含む）には、そのコード自体の責務・意味だけを書く。書いてはいけない4類型:

1. **作業経緯・実装判断の理由・値の由来。** 由来を書くと外部が変わったとき追従が必要になり、漏れて嘘コメントになる。値の意味（「円・税込」）だけ書く
2. **他モジュール/他レイヤーへの依存の明言**（その型自体は依存していない場合）。依存が生じるのは値を渡すロジック側なので、説明もそちら側に書く
3. **未実装機能・将来計画への言及。** まだ存在しないものを「将来追加」と書かない
4. **作業トラッキング情報。** issue 番号をコードやエラーメッセージに埋めない

**書くなら意味を書く。** nullable フィールドの description は「null が何を表すか」。「持たない場合は null」のような同語反復は無内容。

extrinsic な補足が必要なら PR 説明かインラインレビューコメントへ回す。

### コメント要否の4分類

既定は「書かない」。ただし**局所のコードだけ見ると業務的意味が欠落・誤解される**ケースは例外的に文脈付きで残す。

| コードとして | 業務上の意味 | 判断 |
| --- | --- | --- |
| 正しい | 正しい | **残さない** |
| 正しい | 不明/誤解される | **残す** |
| 正しくない | 正しい | **残す** |
| 正しくない | 不明 | **残す**（可能ならコードごと消す） |

2行目が上記③と衝突して見えるが、**局所で業務意味が読めない場合は誤解防止を優先**する。その場合も issue 番号は付けず、概念的なトリガー条件で書く。

## コメントの記法

- **ブロックコメント（`/*` で開くもの）は JSDoc 用途のみ**（型・クラス・メソッド・ファイル概要）
- それ以外は `// ...` の行コメント。**複数行でもブロックコメントを使わず `//` を重ねる**（TODO / FIXME も同様）

## 型

- **不要な `as` 型アサーション（`as const` 含む）を排除する。** 型推論で足りるなら付けない。既存コードが `as const` を使っていても、新規追加分では不要なら省く
- **`T | undefined` の絞り込みは `!` ではなく明示的な `if (x === undefined)` ガード**で行う。到達不能で冗長になってよい。`!` はコンパイラを黙らせるだけで、不変条件が崩れたとき無防備。冗長なガードには「なぜ到達しないか」を `//` で添える
  - `arr.at(-1)` は常に `T | undefined` を返す。`slice(-1)[0]` は（`noUncheckedIndexedAccess` 無効なら）`T` になるという差がある
- **過度に高機能な仕組みを「隣接コードとの一貫性」だけで採用しない。** 要件が単純なら `as const satisfies Record<K, V>` のような素直な実装を選ぶ。迷ったら ①その仕組みの機能のうち今回実際に使うものは何か ②使わない機能の複雑さコスト を並べて比較する。既存と違う形式を意図的に採るなら、レビュー摩擦を避けるため設計ドキュメントに理由を書く

## ログ

**メッセージ ＋ コンテキストオブジェクト**の構造化スタイルで書き、メッセージ文字列に template literal で値を埋め込まない。

```ts
// NG
logger.error(`corporatePricingPlanId の取得に失敗しました: ${id}`);
// OK
logger.error("corporatePricingPlanId の取得に失敗しました", { corporateBillingUnitDocumentId: id });
```

値を埋め込むと null/undefined が混入して `"id: undefined"` のような文字列になり、ログ検索やアラートで誤検出を生む。構造化しておけば `jsonPayload.context.id` で集計・フィルタできる。

**ログ文字列を変更したら、旧文字列を grep しているダッシュボード・アラートがないか確認する。**

## 設計判断

**「既存 X を再利用/再現できる」と見積もるときは、出力の形だけでなく計算経路を末端の sub-service まで辿る。** 出力形の一致と計算ロジックの一致は別物で、両方を経路で裏取りする。入口だけ見て「小整形で再構築可能」と判断すると、実装着手時に結合の深さが露見してレビューをやり直すことになる。
