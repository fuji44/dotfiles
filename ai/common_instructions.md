# Global AI Instructions

このファイルは全てのプロジェクトで共通して参照されるAIアシスタント向けのガイドラインです。

## 動作原則

- セキュリティに関わる情報（APIキー、パスワード等）は決して出力しない。
- 日本語で回答する（特別な指示がない限り）。
- **応答に書く時刻は JST に変換し、`8/14 00:12 JST` のように帯を明示する。** 実行環境の TZ は UTC のことがあり、ファイルの mtime・`date`・ログ・API 応答はそのまま読むと UTC になる。UTC のまま出してよいのは、API のクエリ値やコード中の ISO 文字列のように機械が読む値だけ。
- 実行すべきコマンドや修正箇所のコンテキストを明示する。

## スキルを探す

作業に着手する前に、**その作業を扱うスキルがあるかを一覧の description で確認する。** 会話・調査・
実装・外部サービスやツールの操作を問わない。

**スキルを実行している最中でも探す。** 手順書に沿っていると探索が止まりやすいが、手順書は自分が
扱う対象のことしか書いていない。**扱う対象が切り替わったら探し直す** — 別のサービスへ投稿する、
別の形式で書く、別のツールを動かす、といった場面が該当する。

スキル同士は互いの名前を書かない。参照を静的に張ると、改名・統合のたびに参照元が黙って嘘になる
（検証されない外部への依存。下記「ドキュメンテーションコメントの範囲」と同じ理由）。探索は都度行う。
例外は、扱う範囲の境界を示すために別スキル名を挙げる場合（description で「これは扱わない、
そちらは X」と書くもの）。これは依存ではなく、誤起動を防ぐための情報。

## 破壊的な操作は確認を求める

次は実行前に明示的な確認を求める。**機構的に止める仕組みがある環境では、そちらが先に働く。** 機構が無い環境ではこの節が唯一の歯止めになるので、二重になっても残す。

- `git push`（リモートへの反映）と履歴の改変（`rebase` / push 済みコミットの `amend`）
- 作業ツリーを破壊しうる操作（`reset` / `checkout -- <path>` / `restore` / `clean` / `stash drop` / `branch -D` など、変更を失う恐れのあるもの）
- 広範囲の削除・一括上書き（`rm -rf` でツリーを消す、glob で多数を消す、複数ファイルへの `sed -i`）
- システム全体・ツールチェーンへの変更（OS 設定ファイル群、グローバルインストール）

**権限昇格（`sudo`）だけは、依頼があっても実行前に確認する。** 他は明示的に依頼されていれば確認を省いてよい。

## ツールの利用方針（組み込みツールの優先）

専用の組み込みツール（ファイル閲覧・編集、検索、Webリソース取得など）が存在するタスクに対して、シェルコマンドで代用してはならない。

- **ファイル閲覧**: `cat`, `head`, `tail`, `less` ではなく、ファイル閲覧ツールを使用する
- **ファイル編集**: `sed`, `awk`, `echo >`, `cat <<EOF` ではなく、ファイル編集・置換ツールを使用する
- **検索**: `grep`, `find` ではなく、コード・ファイル検索ツールを使用する
- **Web情報取得**: `curl`, `wget` ではなく、Webコンテンツ読み取り（fetch / read_url）ツールを使用する

### シェルコマンドの実行基準

シェルコマンドの実行は、テスト実行、ビルド、パッケージ管理、Git操作など、専用の組み込みツールが提供されていない外部プロセスの実行に限り使用すること。

## コメント

コメント（JSDoc・`//`・テストの説明文字列・zod/OpenAPI の `description` を含む）には、そのコード自体の責務・意味だけを書く。書いてはいけない4類型:

1. **作業経緯・実装判断の理由・値の由来。** 由来を書くと外部が変わったとき追従が必要になり、漏れて嘘コメントになる。値の意味（「円・税込」）だけ書く。**モジュール/レイヤーの配置理由**（「本来 X に置きたいが依存の都合でここ」）もここに含む
2. **使われ方・参照元への言及。** 下記「ドキュメンテーションコメントの範囲」
3. **未実装機能・将来計画への言及。** まだ存在しないものを「将来追加」と書かない
4. **作業トラッキング情報。** issue 番号をコードやエラーメッセージに埋めない

**書くなら意味を書く。** nullable フィールドの description は「null が何を表すか」。「持たない場合は null」のような同語反復は無内容。

extrinsic な補足が必要なら PR 説明かインラインレビューコメントへ回す。

### ドキュメンテーションコメントの範囲

**ドキュメンテーションコメントは、そのシンボル自身の定義を記述する。** どう使われるか・どこから参照されるかは、シンボル自身ではなく外部が決めることであり、書けばそれ自体が外部への依存になる。コード上の依存であれば型検査がドリフトを捕まえるが、文章だけの依存は誰も検証しないため、外部が変わった時点で静かに嘘になる。

判定は「**この宣言を変更しないまま、その記述が嘘になりうるか**」。なりうるなら書かない。粒度は問わない。

- 関数・メソッド — 「〜に用いる」「〜の前に呼ぶ」
- 型・値オブジェクト — 「〜モジュールへ渡される」「〜層で変換される」
- ファイル概要 — 「〜から参照される」

特別な使い方を伝える必要があるときは、**規定ではなく一例として書く**（`@example` など、例であることが記法から分かる形にする）。一例なら外部が変わっても「例が古い」だけで済み、宣言の意味自体は嘘にならない。ただし陳腐化はするので、変わりにくい代表例に留める。

### コメント要否の4分類

既定は「書かない」。ただし**局所のコードだけ見ると業務的意味が欠落・誤解される**ケースは例外的に文脈付きで残す。

| コードとして | 業務上の意味 | 判断 |
| --- | --- | --- |
| 正しい | 正しい | **残さない** |
| 正しい | 不明/誤解される | **残す** |
| 正しくない | 正しい | **残す** |
| 正しくない | 不明 | **残す**（可能ならコードごと消す） |

2行目が上記③と衝突して見えるが、**局所で業務意味が読めない場合は誤解防止を優先**する。その場合も issue 番号は付けず、概念的なトリガー条件で書く。

## コメントの記法

- **ブロックコメント（`/*` で開くもの）は JSDoc 用途のみ**（型・クラス・メソッド・ファイル概要）
- それ以外は `// ...` の行コメント。**複数行でもブロックコメントを使わず `//` を重ねる**（TODO / FIXME も同様）

## 型

- **不要な `as` 型アサーション（`as const` 含む）を排除する。** 型推論で足りるなら付けない。既存コードが `as const` を使っていても、新規追加分では不要なら省く
- **`T | undefined` の絞り込みは `!` ではなく明示的な `if (x === undefined)` ガード**で行う。到達不能で冗長になってよい。`!` はコンパイラを黙らせるだけで、不変条件が崩れたとき無防備。冗長なガードには「なぜ到達しないか」を `//` で添える
  - `arr.at(-1)` は常に `T | undefined` を返す。`slice(-1)[0]` は（`noUncheckedIndexedAccess` 無効なら）`T` になるという差がある
- **過度に高機能な仕組みを「隣接コードとの一貫性」だけで採用しない。** 要件が単純なら `as const satisfies Record<K, V>` のような素直な実装を選ぶ。迷ったら ①その仕組みの機能のうち今回実際に使うものは何か ②使わない機能の複雑さコスト を並べて比較する。既存と違う形式を意図的に採るなら、レビュー摩擦を避けるため設計ドキュメントに理由を書く

## ログ

**メッセージ ＋ コンテキストオブジェクト**の構造化スタイルで書き、メッセージ文字列に template literal で値を埋め込まない。

```ts
// NG
logger.error(`corporatePricingPlanId の取得に失敗しました: ${id}`);
// OK
logger.error("corporatePricingPlanId の取得に失敗しました", { corporateBillingUnitDocumentId: id });
```

値を埋め込むと null/undefined が混入して `"id: undefined"` のような文字列になり、ログ検索やアラートで誤検出を生む。構造化しておけば `jsonPayload.context.id` で集計・フィルタできる。

**ログ文字列を変更したら、旧文字列を grep しているダッシュボード・アラートがないか確認する。**

## 設計判断

**「既存 X を再利用/再現できる」と見積もるときは、出力の形だけでなく計算経路を末端の sub-service まで辿る。** 出力形の一致と計算ロジックの一致は別物で、両方を経路で裏取りする。入口だけ見て「小整形で再構築可能」と判断すると、実装着手時に結合の深さが露見してレビューをやり直すことになる。

## 応答テキスト

URL は常に `[表示テキスト](URL)` の markdown リンクで書く。**例外を作らない。** 自動リンク化は
リンク記法が無いときだけ働き、周囲の記号との境界を誤判定する。以下はいずれも実際に壊れた例。

| 書き方 | 壊れ方 |
| --- | --- |
| `**http://localhost:36885**` | `**` が装飾として消えず、そのまま文字として出る |
| `（http://example.com）` | 末尾の `）` を URL に巻き込む |
| `詳細はhttp://example.com` | 日本語の直後で境界を誤判定する |

強調したいときも **リンク記法を内側にしない**。`**[表示テキスト](URL)**` の順で囲む。

裸で置いてよいのは **GitHub に投稿するテキストだけ**（issue / PR の本文・コメント）。あちらは
リッチ表示のために bare URL が正しく、規約が逆になる。混同しないこと。

## Artifact に図を載せる（Claude Code）

Artifact のネイティブ mermaid 描画は**ページ読み込み時に一度だけ DOM を走査する**。
`<pre class="mermaid">` は**静的マークアップとして書き出す**。スクリプトで挿入した図は
変換されず、**エラーも出さずに消える**（CSP で CDN が遮断されるため、自前で mermaid を
呼ぶ回避策も無い）。ページを JSON + 描画スクリプトで組むときも、図だけは静的側に置く。
図の導出はページを生成する時点で済ませ、出力は静的にする。

`<pre>` の中では `<br/>` と `-->` を HTML エンティティで書く（`&lt;br/&gt;` / `--&gt;`）。
生で書くとブラウザが HTML として解釈し、mermaid のパーサに届く前に壊れる。

**描画失敗は例外を投げないので、公開後に図が出ているかを目視で確かめる。**
