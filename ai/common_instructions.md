# Global AI Instructions

このファイルは全てのプロジェクトで共通して参照されるAIアシスタント向けのガイドラインです。

## 動作原則

- セキュリティに関わる情報（APIキー、パスワード等）は決して出力しない。
- 日本語で回答する（特別な指示がない限り）。
- **応答に書く時刻は JST に変換し、`8/14 00:12 JST` のように帯を明示する。** 実行環境の TZ は UTC のことがあり、ファイルの mtime・`date`・ログ・API 応答はそのまま読むと UTC になる。UTC のまま出してよいのは、API のクエリ値やコード中の ISO 文字列のように機械が読む値だけ。
- 実行すべきコマンドや修正箇所のコンテキストを明示する。

## スキルを探す

作業に着手する前に、**その作業を扱うスキル（規則やプラグインも含む）があるかを一覧の description で確認する。** 会話・調査・
実装・外部サービスやツールの操作を問わない。

**スキルを実行している最中でも探す。** 手順書に沿っていると探索が止まりやすいが、手順書は自分が
扱う対象のことしか書いていない。**扱う対象が切り替わったら探し直す** — 別のサービスへ投稿する、
別の形式で書く、別のツールを動かす、といった場面が該当する。

## 破壊的な操作は確認を求める

次は実行前に明示的な確認を求める。**機構的に止める仕組みがある環境では、そちらが先に働く。** 機構が無い環境ではこの節が唯一の歯止めになるので、二重になっても残す。

- リモートへの反映と、共有済みの履歴の改変
- 作業ツリーの保存していない変更を失いうる操作
- 広範囲の削除・一括上書き
- システム全体・ツールチェーンへの変更（OS の設定、グローバルなインストール）

**権限の昇格だけは、依頼があっても実行前に確認する。** 他は明示的に依頼されていれば確認を省いてよい。

**変異など、変更を戻す前提の作業に入る前に、作業ツリーの変更を保存してクリーンにする。**

git では `push`、`rebase`・push 済みコミットの `amend`、`reset`・`checkout -- <path>`・`restore`・`clean`・`stash drop`・`branch -D` が該当し、保存は commit か stash で行う。シェルでは `rm -rf` でのツリーの削除、glob での多数の削除、複数ファイルへの `sed -i`、権限の昇格の `sudo` が該当する。

## ツールの利用方針（組み込みツールの優先）

専用の組み込みツール（ファイルの閲覧・編集、検索、Web の取得など）があるタスクは、専用のツールで行う。シェルは、テスト・ビルド・パッケージ管理・バージョン管理など、専用のツールが無い外部プロセスの実行に使う。

シェルでは、閲覧の `cat`・`head`・`tail`・`less`、編集の `sed`・`awk`・`echo >`・`cat <<EOF`、検索の `grep`・`find`、Web の取得の `curl`・`wget` が代用に当たる。

## コメント

コメント（ドキュメンテーションコメント・行コメント・テストの説明文・スキーマ定義の説明文を含む）には、そのコード自体の責務・意味だけを書く。書いてはいけない4類型:

1. **作業経緯・実装判断の理由・値の由来。** 由来を書くと外部が変わったとき追従が必要になり、漏れて嘘コメントになる。値の意味（「円・税込」）だけ書く。**モジュール/レイヤーの配置理由**（「本来 X に置きたいが依存の都合でここ」）もここに含む
2. **使われ方・参照元への言及。** 下記「ドキュメンテーションコメントの範囲」
3. **未実装機能・将来計画への言及。** まだ存在しないものを「将来追加」と書かない
4. **作業トラッキング情報。** 課題管理の番号をコードやエラーメッセージに埋めない

**書くなら意味を書く。** 値が無いことを許すフィールドの説明には、無いことが何を表すかを書く。「持たない場合は null」のような同語反復は無内容。

コードの外にある補足が必要なら、変更の説明やレビューのコメントへ回す。

### ドキュメンテーションコメントの範囲

**ドキュメンテーションコメントは、そのシンボル自身の定義を記述する。** どう使われるか・どこから参照されるかは外部が決めることであり、書けばそれ自体が検証されない外部への依存になる。

判定は「**この宣言を変更しないまま、その記述が嘘になりうるか**」。なりうるなら書かない。粒度は問わない。

- 関数・メソッド — 「〜に用いる」「〜の前に呼ぶ」
- 型・値オブジェクト — 「〜モジュールへ渡される」「〜層で変換される」
- ファイル概要 — 「〜から参照される」

特別な使い方を伝える必要があるときは、**規定ではなく一例として書く**（例であることが記法から分かる形にする）。一例なら外部が変わっても「例が古い」だけで済み、宣言の意味自体は嘘にならない。ただし陳腐化はするので、変わりにくい代表例に留める。

- **概要（1行目）を必ず書く。** 引数や戻り値の説明だけのブロックにしない。注釈だけを目的とするブロック（非推奨の印、API 定義の埋め込みなど）は除く
- **説明は公開シンボルに直接付け、ファイル（モジュール）単位の概要は原則として書かない。** シンボル側に書けば、ファイル概要にはその重複しか残らないことがほとんどである。単一クラスのファイルなら、説明はクラスに書く

### コメント要否の4分類

既定は「書かない」。ただし**局所のコードだけ見ると業務的意味が欠落・誤解される**ケースは例外的に文脈付きで残す。

| コードとして | 業務上の意味 | 判断 |
| --- | --- | --- |
| 正しい | 正しい | **残さない** |
| 正しい | 不明/誤解される | **残す** |
| 正しくない | 正しい | **残す** |
| 正しくない | 不明 | **残す**（可能ならコードごと消す） |

2行目が上記③と衝突して見えるが、**局所で業務意味が読めない場合は誤解防止を優先**する。その場合も issue 番号は付けず、概念的なトリガー条件で書く。

## コメントの記法

- **ドキュメンテーションコメントの記法は、ドキュメンテーションコメント（型・クラス・メソッド・ファイル概要）にだけ使う**
- それ以外は行コメントで書く。**複数行でも行コメントを重ねる**（TODO / FIXME も同様）

## 型

- **型検査・静的解析などの安全機構を崩さない。** 型の断定、値が無いことはないという断定、検査や解析の抑止は、機構が守っている不変条件をその場所だけ外し、不変条件が崩れたときに無防備になる。崩さずに書ける形（型推論・型の絞り込み・明示的な分岐・型の付いたモック）を先に探す
- **値が無いかもしれない型は、断定ではなく明示的な分岐で絞り込む。** 到達しない分岐で冗長になってよい。冗長な分岐には「なぜ到達しないか」をコメントで添える
- **過度に高機能な仕組みを「隣接コードとの一貫性」だけで採用しない。** 要件が単純なら素直な実装を選ぶ。迷ったら ①その仕組みの機能のうち今回実際に使うものは何か ②使わない機能の複雑さコスト を並べて比較する。既存と違う形式を意図的に採るなら、レビュー摩擦を避けるため設計ドキュメントに理由を書く
- **コードレビューで防げる程度の誤りを、型や証拠オブジェクトで使われ方まで縛らない。** 仕組みが無いと何が起き、それはレビューで見えるかを先に比べる

## ログ

**メッセージ ＋ コンテキスト**の構造化スタイルで書き、メッセージ文字列に値を埋め込まない。

値を埋め込むと、値が無いときに `"id: undefined"` のような文字列が混入し、ログ検索やアラートで誤検出を生む。構造化しておけば、コンテキストのフィールドで集計・フィルタできる。

**ログ文字列を変更したら、旧文字列で検索しているダッシュボード・アラートがないか確認する。**

## コードと文書の置き場

ソースコードが唯一の真実である。**説明は、説明する対象の実体に最も近い場所に置く。** 近い順に、シンボルに付くコメント、シンボルに付かないコメント、同じ版管理の下の文書、版管理の外の文書。

- **コードだけで表せるなら書かない。** 命名・型・構造で表せないかを先に考える
- **書くのはコードから読み取れないことだけ**（背景・意図・決定とその理由・外部の前提）。読み取れることは、要約や一覧の形でも書かない
- **置き場は対象の実体で決める。** シンボルの説明はそのシンボルのドキュメンテーションコメント、複数のシンボルにまたがる説明はそれを束ねる単位の入口の文書、運用の手順・業務の決定はその読み手が使う場所
- **文書から実体をたどれるように保つ。** 文書の仕組みに関連付けの手段（参照の記法・リンク）があれば使う。無ければ変わりにくい名前で示し、ファイルパスや行番号を書き写さない

## 設計判断

**「既存 X を再利用/再現できる」と見積もるときは、出力の形だけでなく計算経路を末端まで辿る。** 出力形の一致と計算ロジックの一致は別物で、両方を経路で裏取りする。

**共通化のために継承を使わない。** 継承は、ライフサイクルが同一で処理が不可分であることを宣言する結合であり、共通コードの置き場ではない。処理を共有したいなら純関数に切り出し、各実装が合成する。組み立て順の一貫性が要るなら、その順序だけを 1 つの純関数に閉じ込める。

**ドキュメント型のデータベースで値が無いことは null で表す。** 項目を持たない形は、項目を足す前からあるデータとの後方互換のときだけにする。消すときも null を書く。

**複数の製品が実装している公開の仕様を、既定かつ第一の選択肢にする。** 製品固有の仕様は、その製品を使う場面で標準を補ったり上書きしたりする付随情報として扱い、標準で足りる部分には重ねない。例: エージェント向けの指示ファイルは `AGENTS.md` を置き、製品固有のファイルは必要なときだけ足す。

**調査の結論は、集めた証拠から出す。** 依頼に添えられた見立てや一般原則は仮説として扱い、証拠と合わなければ合わないと書く。書き終えたら、証拠の節と結論の節が同じ方向を向いているかを読み返す。選択肢のコストが同じ（メソッド・命名・置き場の選択など）なら、明文化された規約と同じモジュールの一貫性を既定にする。

**本筋でない改善と、まだ無いケースは、別の課題に出す。** 影響範囲の広い改善・後の機能への備え・別の課題で決めると明示された論点を、本筋の設計の制約にしない。まだ無いケースに備える前に、それが今の仕様と実装にあるかを確かめる。

**レビューの指摘に応えて例外や仕組みが増えてきたら、次の対策を足す前に、指摘の多くを生んでいる構成を特定し、それを外した最小の案と比べる。** 例外ごとに統一したら何が起きるかを書き出し、機能や安全を損なうものだけを残す。

## 変更の単位

**コミットは目的ごとに分けて積む。** 既存の不具合の修正・既存の挙動の変更・新しい機能は、それぞれ別のコミットにする。機械的な変更（他のブランチの取り込み・一括の置換・生成物の更新）と、判断を含む変更も分ける。目的ごとに積んでおけば、レビューの前に PR を分けるときの積み直しが安く済む。

## 応答テキスト

URL は常に `[表示テキスト](URL)` の markdown リンクで書く。**例外を作らない。** 自動リンク化は
リンク記法が無いときだけ働き、周囲の記号（強調・括弧・直前の日本語）との境界を誤判定する。

強調したいときも **リンク記法を内側にしない**。`**[表示テキスト](URL)**` の順で囲む。

投稿先のテキストに記法の規約が別にあるときは、そちらに従う。投稿先によっては URL の書き方が逆になる。

## 知識の扱い

| 性質 | 置き場所 |
| --- | --- |
| 機構で判定できる禁止 | 権限設定や実行前の検査などの機構 |
| 起動の瞬間が無い制約 | 常時読み込まれるインストラクション |
| 起動の瞬間がある手順 | トリガーで起動する手順書 |
| 汎用の事実・経験・判断（確度を問わない）と、規範の理由 | 環境をまたいで共有する知識基盤 |
| 環境固有・業務固有のこと、一般化できるか迷う学び | エージェントの組み込みの記憶 |

道具の操作や設計判断に着手する前に、知識基盤が使える環境なら、過去の落とし穴や判断を検索する。汎用の学び（道具の思わぬ挙動、人の指摘や方針、選んだ判断、覆った前提）を得たら、その場で出来事として記録する。

- **一次情報から引けるものは写さない。** 腐らない値でも、毎回必要なのでなければ識別子だけを残す
- **共有される場所に、環境固有の値と業務の機密を書かない。** パス・ホスト名・環境変数は他の環境で
  解決できない。業務から得た学びも同じように書く。固有名詞と内部の識別子は除いて一般化する
- **汎用の知識と環境固有の知識を1か所に混ぜない。**
- **確度が足りないうちは昇格しない。** 1回の観測は記録に留める。人が決めた規約は確度を問わず昇格を提案する。昇格の承認は人がする
- **昇格したら移行元から内容を消す。** 内容を持たない思い出すための足がかりは残してよい。
  ただし機構がすべての環境に届かないなら、散文の歯止めは別の層の保険として残す
- **食い違いを見つけたら、自分で決めずに人に判定を仰ぐ。**

### 製品の挙動には確認した時点を添える

製品の挙動は版を重ねると変わる。**特定の製品の挙動・仕様・制約を書くときは、置き場を問わず、確認した時点を事実ごとに添える。** 文書全体に1つだけ付けると、改訂のたびにすべての事実を確かめ直すことになる。

- **日時は必須。** 確認した日（必要なら時刻）を書く
- **版も原則として必須。** 版の番号が無い・取れないときは、ビルド番号やコミットハッシュで代替する。版があっても、それだけで特定できないときはビルド番号やコミットハッシュで補う。例: `確認: 2026-11-17 / <製品> v1.2.3（build 4567）`
- **環境は、識別子が宣言されていれば常に添える。** 環境に依る挙動かどうかは、観測した時点では分からない。プロセスが動いた一番内側の環境を書き、作業対象のシステムが動く環境で観測したならそれも書く。例: `確認: 2026-11-24 / <製品> v1.2.3 / 作業環境 <識別子>`、`… / 稼働環境 <識別子>`。宣言の置き場と識別子の付け方は知識基盤の使い方にある。宣言が無ければ環境は書かない
- 確認できない記述を移してきたときは、確認日と版が不明であることと、いつ時点で存在した記述かを書く

書いた内容を使うたびに版を確かめ直すことはしない。記述と実際の挙動が食い違ったとき、または長い期間が経った記述を使うときに検証し直す手がかりにする。食い違ったら実物を正とし、確かめ直した時点で書き換える。
